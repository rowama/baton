# Worker status says which catalog it read and exactly why a generated profile is no longer offered

## Request

### Problem

On 2026-11-08, right after `2026-11-cli-model-routes` wrote eight per-model profiles (run from the repo checkout), `baton workers status` run from a stale uv tool install flagged all eight as:

```
profile codex-gpt-6-astra: unverified; no longer offered here (route gone, not found or not declared); kept
```

Both CLIs were reported `ready`, so the real cause was that the `baton` on PATH read an older `known-workers.yaml` (from its packaged `baton/_data/defaults`) that has no per-model routes. Nothing in the output said that; it took reading `resources.py` and checking `which baton` to find it.

The flag text lumps three different situations into one, and status never says which catalog it read:

- the route is not in the catalog in use (catalog changed, or a different runtime's catalog is being read);
- the harness is not found or not logged in;
- the declared resource was removed (or no longer lists the model, or lost its credential).

Each generated profile already carries `generated.known_workers_sha256` (0079), the catalog it was written from, so a catalog mismatch can be detected for free.

Who meets this beyond development: an owner whose project pins an older runtime (§14.1 launcher, `$BATON_HOME/versions/<v>/`) shares `~/.baton/workers/` with every other runtime on the machine, so profiles generated by a newer runtime show as "no longer offered" there. Profiles are kept (correct), but the message sends the owner looking in the wrong place.

### Acceptance criteria

- `baton workers status` (and `--json`) names the known-workers file it read and its short sha256.
- A generated profile the inputs no longer offer is flagged with one specific reason, in plain words, chosen in this order:
  1. its model is retired (unchanged wording);
  2. its harness is not usable here: the discovery problem (not installed / not logged in);
  3. its resource is gone from the machine resources, or no longer offers the model, or has no credential;
  4. no route in the catalog in use produces it; and, when the profile's `known_workers_sha256` differs from the catalog in use, the flag says it was generated from a different known-workers catalog (both short shas) and that a different Baton runtime or an updated catalog may be the cause;
  5. any other skipped route: the `plan_profiles` skip reason for that route.
- `baton workers setup`'s `kept <profile>: …` lines use the same reasons (they come from the same function).
- The `--json` `generated.<name>` entry gains `flag_code` (`retired`, `harness_unusable`, `resource_gone`, `route_gone`, `skipped`) beside `flag`, and `catalog_mismatch: true|false`.
- Nothing is removed or rewritten; ownership, refresh and keep rules (0079) are unchanged.
- Tests cover each reason, the mismatch note (same sha: no note), and the catalog line; `pytest` green.

## Design

### Doc edits

- `design/workers.md` §6.4, *Refresh and repeat runs*: the "kept and flagged" bullet lists the specific reasons and the catalog-mismatch note; the status description says it names the catalog file and sha it read.

### Decisions

- Relies on 0079 (generated files carry `known_workers_sha256`; not-offered profiles are kept and flagged). No new decision: this only makes the flag specific.

## Plan

Minor: one slice, *Specific not-offered reasons and catalog line* (effort S). `_not_offered` in `resources.py` takes the detections, resources and catalog sha; matches each profile back to its route by `provider` + `model_id` (or provider default for an alias profile) and `resource`; the CLI's `workers status` prints `catalog: <path> (sha <12 hex>)` as its second line.
