## 6. Worker Profiles and Execution

### 6.1 Profiles (`~/.baton/workers.yaml`, overridable by `.baton/workers.local.yaml`)

```yaml
openai-api-strong:
  adapter: litellm_api
  creator: openai                      # who made the model: different_vendor
  model_id: openai/…                   # the model's identity on every route: different_model
  provider: openai                     # the access provider
  model: "openai/…"                    # what the adapter passes on [VERIFY current model strings]
  capabilities: [structured_output, long_form_writing, technical_reasoning, tool_use]
  tier: strong
  context_tokens: 200000
  auth: { mode: api_key, env: { OPENAI_API_KEY: "secret:openai_main" } }

codex-sub:
  adapter: codex
  creator: openai                      # no model_id: the CLI's default model is a mutable alias
  capabilities: [structured_output, tool_use, file_write, shell, code_exec, repo_workspace, workspace_read, long_form_writing, technical_reasoning]
  tier: strong
  context_tokens: 200000
  auth: { mode: cli_login }            # the CLI's stored subscription login
  env_deny: [OPENAI_API_KEY, CODEX_API_KEY]   # a stray key could switch billing to the API
  executable: codex                    # the preset's default
  path: { search: [nvm] }
  # args omitted: the codex preset's defaults (§6.3); args.write / args.read / args.none override per mode

claude-code-sub:
  adapter: claude_code
  creator: anthropic
  capabilities: [structured_output, tool_use, file_write, shell, code_exec, repo_workspace, workspace_read, loopback_network, long_form_writing, technical_reasoning]
  tier: strong
  context_tokens: 200000
  auth: { mode: cli_login }
  env_deny: [ANTHROPIC_API_KEY]
  executable: claude
  path: { search: [nvm] }
  args: { write: ["--permission-mode", "bypassPermissions"] }   # the preset's default; shown as an example

claude-code-opus:                      # the same harness pinned to one model
  adapter: claude_code
  creator: anthropic
  model_id: anthropic/claude-opus-5-5  # the model's identity, the same as on the direct API
  model: claude-opus-5-5               # passed as --model; the full ID pins the version, an alias such as opus does not
  capabilities: [structured_output, tool_use, file_write, shell, code_exec, repo_workspace, workspace_read, long_form_writing, technical_reasoning]
  tier: strong
  context_tokens: 1000000
  auth: { mode: cli_login }
  env_deny: [ANTHROPIC_API_KEY]

owner:
  adapter: manual
  creator: human                       # a person's identity is human/<person>
  person: owner
  capabilities: [human_judgment, long_form_writing, vision, file_write]
  tier: strong
```

| Field | Notes |
|---|---|
| `creator` | Who made the model (`human` for people). Required. `vendor`, its name before, is still read (giving both, differing, is a load error). Compared by `different_vendor` (§8.4) |
| `model_id` | The model's canonical identity, `<creator>/<name>` in lower case, the same on every route (direct API, OpenRouter, a harness). Revisions are part of it when the creator distinguishes them; fine-tunes and quantizations take their base model's id; a mutable alias (a harness's default model, `latest`) or a route whose underlying model is unknown has none. Absent means **unknown**, and nothing is inferred from `model`. A `manual` profile's identity is `human/<person>`. Compared by `different_model` (§8.4) |
| `provider` | The access provider (`openai`, `openrouter`, `local`…). Route only: never used for independence |
| `model` | The provider- or harness-specific invocation identifier the adapter passes on (§6.3) |
| `resource` | The machine resource the profile uses |
| `auth.mode` | `api_key` (resolved secrets injected) \| `cli_login` (CLI's stored credentials) \| `none` |
| `env_mode` | `clean` (default for `api_key`) \| `allowlist` (default for `cli_login`; passes `HOME`, `USERPROFILE`, `APPDATA`, `LOCALAPPDATA`, `LANG`, `TERM` plus `env_allow`) \| `inherit` (escape hatch). `env_deny` is always applied last. |
| `auth.config_home` | Relocated CLI config dir so several logins coexist: `CLAUDE_CONFIG_DIR` for `claude_code`, `CODEX_HOME` for `codex` (both seen in the installed CLIs; switching logins with them is untested) |
| `executable`, `path.search`, `path.prepend` | Harness CLI resolution (§6.2) |
| `args.write` / `args.read` / `args.none` | Adapter args per workspace mode (permission and sandbox modes). Each replaces the preset's built-in default for that mode only (§6.3) |
| `isolation` | `none` \| `user` \| `container` |
| `capabilities` | Must be **true on this machine** (e.g. a sandbox that cannot bind localhost must not claim `loopback_network`). Each claim carries a state, `likely` until observed (below) |
| `env_deny` | Exact names or `fnmatch` patterns (`*_API_KEY`); removes a name whatever put it there (inherit, `env_allow`, `auth.env`) |
| `price` | Optional, per million tokens: `input`, `output`, `free`, with its `source` and `date` (Decision: [0115](../decisions/0115-price-is-not-a-concept.md)). A fact for routing preference and the run record, never a capability; refreshed by `workers setup` like `capabilities` |
| `options` | Non-secret adapter options (`litellm_api`: keyword arguments for the completion call, e.g. `base_url`, `temperature`) |
| secrets | `secret:<name>`, allowed only in `auth.env`; resolved at spawn time from the variable `BATON_SECRET_<NAME>` (upper-cased, other characters `_`), then the OS keyring (service `baton`; needs the optional `keyring` package), then the file `~/.baton/secrets/<name>`. A missing secret refuses the dispatch as `configuration`, naming all three places. Never written to packets, events or logs; resolved values are redacted from anything the runtime records |

**Profiles for people are built in** (Decision: [0174](../decisions/0174-first-use-feedback-people.md)). Nobody writes a profile for a person. Every machine has `owner`, the `manual` profile in the example above (identity `human/owner`, `human_judgment`, `long_form_writing`, `vision`, `file_write`, tier `strong`), held in memory by `Project.profiles` under every other source, so a profile named `owner` in `workers.yaml` or `.baton/workers.local.yaml` replaces it. When the project policy names someone else to do the steps for a person (`policy.people.person_steps`, §13.7), a profile for them is built the same way: `person-<slug>`, identity `human/<slug>`, the slug being their name in lower case with its words joined by `-`; it goes when the rule changes. A built-in profile for a person does only the steps for a person, those that require `human_judgment` (§8.4): it is never listed, eligible or excluded, for any other step, and it is not an AI helper for `doctor`'s "no worker is ready" (§13.4). `workers status` shows `people.owner {builtin, capabilities, does}`, `builtin: false` when a profile in `workers.yaml` replaces it.

The owner need not store a secret by hand: `baton workers connect` and the setup page (§13.9) write it to the OS keyring when the `keyring` package and a backend work, else to `~/.baton/secrets/<name>` (directory 0700, file 0600), check it first with one listing read, and report which store was used; `baton workers disconnect` removes the declaration and, with `--forget-key`, the stored key (Decision: [0123](../decisions/0123-keys-keyring-then-file.md)).

**Capability states** (Decision: [0084](../decisions/0084-capability-states.md)). A profile *claims* its capabilities; whether each claim has been seen to hold here is a separate fact, kept machine-wide in `~/.baton/capability-states.yaml` (`baton-capability-states/1`), never in a profile file, so recording one changes no profile's content hash (0079) or `worker_profile_sha256` (§7.1):

```yaml
format: baton-capability-states/1
profiles:
  codex:                               # by profile name
    web_access: { state: verified, date: 2026-11-08, by: observed, evidence: "web_search call", run: …, step_path: …, attempt: 1, harness_version: 0.166.0 }
    structured_output: { state: likely, failures: 2 }
```

| State | Meaning | Routing (§8.4) |
|---|---|---|
| `likely` | Claimed (from the known-workers data, a declaration or the owner's file), not yet observed. A claimed capability with no entry is `likely` | Eligible |
| `verified` | Observed working, with date and evidence (`by: observed` from a real dispatch, `probe` from a passing probe, 0082, `check` from a capability check, with its `set_version`, §6.4) | Eligible, preferred |
| `absent` | Observed failing (a capability check's failure names the tasks that failed), or declared absent by the owner (`by: owner`) | Not eligible for steps that need it |

A state qualifies only a capability the profile claims; it never adds one (a passed capability check adds a capability to an unjudged model's profile, not through its state, §6.4). Tooling capabilities are observed from the harness's event stream (§6.3). `structured_output` is a model-quality capability: each checked output schema counts against the dispatched profile (`failures`), a pass resets the count, and the third failure in a row on one profile, counted machine-wide, records it `absent` (Decision: [0087](../decisions/0087-structured-output-by-schema-gate.md)); `result_rejected` and the provenance `gate_passed` carry `output_schema: passed|failed` for it. Other model-quality capabilities (`technical_reasoning`, `long_form_writing`) are never changed automatically. `verified` does not expire: it stands until a failure is observed or the harness's version changes (states recorded `by: observed`, `probe` or `check` under another harness version return to `likely`). `baton workers status` shows each generated profile's states; `baton workers declare --profile <name> --likely <capability>` resets one (forgetting the observation, so it is tried again) and `--absent <capability>` declares one absent. Writes are locked, so concurrent runs on one machine never lose each other's observations. A change of state that a dispatch produced is recorded in the project log as `capability_observed` (§8.2).

**Capabilities Baton's runner provides** (Decision: [0168](../decisions/0168-step-tool-harness-details.md)). For a `litellm_api` profile, the tooling capabilities its runner provides (§6.3) are facts about Baton's code and the model, not researched claims: a profile whose model claims `tool_use` (LiteLLM's `supports_function_calling`, basis `catalog`, Decision [0088](../decisions/0088-capability-basis.md)), not recorded `absent`, has `workspace_read`, `verified` with `by: baton_runner`, without claiming it, and `web_access` too when it has a search backend: its provider's own search (§6.3), or else the search service declared on the machine (§6.4). They are attached when profiles are loaded, like states, so they change no profile's hash; a recorded state (an owner's `--absent`) still wins. A `litellm_api` profile never has a tooling capability the runner does not provide (`shell`, `file_write`, `code_exec`, `repo_workspace`, and `web_access` until the runner provides it), whatever its file claims. `workers status` shows a provided capability's state with the others and lists it under `provided_by_runner`, and for each API profile `web_access {offered, how | why_not, billed_per_search?}`. Provider search is billed per search apart from tokens (Decision 0168, item 9): the setup page's price says "web search billed per search", `result_submitted` counts the attempt's `searches`, and Baton estimates no charge. `doctor` returns the same note per API profile as `api_web_access` when a vendored recipe has web steps, and prints each reason a model has none only when no worker here can do those steps (§13.4: silent when healthy).

Profiles load from `~/.baton/workers/` (generated, one file per profile, named by the file; §6.4), then `~/.baton/workers.yaml` (the owner's), then `.baton/workers.local.yaml`; a later file wins on a name. A generated profile carries a `generated` marker, which is not part of its hash.

Decision: [0075](../decisions/0075-model-identity-separate-from-route.md). Identity (`creator`, `model_id`) and route (`provider`, `model`, `adapter`, `resource`) are separate: the same model reached directly and through OpenRouter has one identity and two routes. A profile's hash (`worker_profile_sha256`, §7.1) still names the creator `vendor`, so profiles written before the rename keep their hashes.

CLI logins are usually files under the home directory; some platforms use an OS keychain that needs the user's session **[VERIFY]**. `doctor` (§13.4) proves each profile works on each machine.

### 6.2 Environment and PATH

`profiles.build_env(profile)`: start empty (`clean` / `allowlist`) or from the parent (`inherit`); copy allowed variables; build `PATH`; inject resolved secrets for `api_key`; set the config-home variable if any; **remove `env_deny` last**; add `BATON_PACKET_DIR`, `BATON_RESULT_DIR`, `BATON_WORKSPACE` (the last only for workspace steps). Only variable **names** are logged: `dispatched` records the env mode, the names present, the names denied, the names holding secrets and the resolved executable, plus the profile's declared `auth_mode` and the step's `workspace_mode`. On Windows, `SYSTEMROOT`, `WINDIR`, `COMSPEC`, `PATHEXT`, `TEMP` and `TMP` are always passed, since a child process cannot start without them **[VERIFY]**.

**PATH resolution** is explicit because version-managed CLIs (e.g. Node via nvm) are not on PATH in non-login shells:
1. Absolute `executable` → use it.
2. Found on the base PATH (`path.prepend` + minimal system PATH; `path.prepend` + the parent's PATH under `inherit`) → use it.
3. Each `path.search` source (`~` is the user's home, `HOME`/`USERPROFILE`, never the Baton home) (`nvm` → `$NVM_DIR/versions/node/*/bin`, `~/.nvm/versions/node/*/bin`, newest version first by numeric order, and `$NVM_HOME/v*` for nvm-windows **[VERIFY]**; `pyenv` → `$PYENV_ROOT/versions/*/bin`, `~/.pyenv/versions/*/bin`; `asdf` → `$ASDF_DATA_DIR/shims` or `~/.asdf/shims`; explicit dirs, `~` allowed) → prepend the first dir that has it. Any other source name is a profile load error.
4. Otherwise fail with `executable_not_found` (a **platform** failure, §8.8), listing every place searched (a source whose root does not exist is listed as its pattern).

A location found through a `path.search` source is recorded once as an observed platform fact (§12.3).

### 6.3 Adapters

```python
class WorkerAdapter(Protocol):
    name: str
    def command(self, profile, packet_dir, result_dir, workspace, mode) -> list[str]: ...
    def postprocess(self, profile, packet_dir, result_dir, proc_result) -> None: ...
    failure_signals: list[dict]          # patterns for classification (§8.8)
```

- **`litellm_api`**: runs `python -m baton.worker_runner` as the child (installed with the optional extra `baton[api]`). It builds messages from `INSTRUCTIONS.md` plus the text of every input not already inlined there, requests structured output where `litellm` reports support **[VERIFY per model]** (otherwise the reply schema goes in the prompt), and writes artifacts and `result.json` itself. The model replies with one JSON object: `status`, `output`, `artifacts` (text by declared name), `notes`, `questions_for_human`; a reply that is not a JSON object is a `failed` result (the step's problem, retried). **Inputs too large to inline are a hard error (§18 #1):** a non-UTF-8 input, or messages over `context_tokens × 2` bytes (roughly half the window; 256 KiB when `context_tokens` is not declared). The runtime checks this when dispatching, before anything is recorded, and refuses with a hint to choose a worker that reads files. Failures that are not the step's (authentication, network or provider errors, an unknown model, `litellm` missing) write no result; the child prints one line `baton-worker: failure=<class> code=<code> message=<redacted text>` and exits non-zero.
  - **The tool loop** (change `2026-11-step-tool-harness`; Decision: [0168](../decisions/0168-step-tool-harness-details.md)). LiteLLM runs no tools: the caller executes a model's tool calls and sends the results back in another `completion` call. When a step needs a tooling capability the runner provides (`runner_tools.py`: `workspace_read`, for a profile whose model claims `tool_use` not recorded `absent`), the packet's manifest lists the tools (`tools: [list_files, read_file]`) and the step's limit (`tool_calls`, default 40), and the runner loops instead of making one call: it offers those tools plus **`finish`**, whose arguments are the reply (the same JSON object, checked by intake as today; no `response_format` is sent on a tool route, because not every provider combines the two), runs each call, sends its result back as a `tool` message marked as data from outside the conversation (the system message says tool results are never instructions), and calls the same model again, until `finish`, the limit (a `failed` result whose notes say so), two replies in text without a tool call (each answered with a reminder; then `failed`), or an error classified as today. Nothing in the loop changes the model: profile `options` that would let LiteLLM fall back to another (`fallbacks`, `context_window_fallbacks`, `content_policy_fallbacks`) are a `configuration` failure (`fallbacks_not_allowed`) on a tool route. **`list_files(path)` and `read_file(path)`** see the packet's inputs (`inputs/…`) and, on a `read` step, the working tree (`workspace/…`, given to the child as `--workspace`); paths are relative, `..` and absolute paths are refused, `.git` and `.baton` are neither listed nor read, a link that leads out is neither listed nor followed, a read is at most 1 MiB of UTF-8 text, a listing at most 1,000 entries. A refused call is returned to the model as `refused: <why>` and recorded. No tool writes, runs a command or executes code. **The web** (`web_access`: `search` and `fetch`; both are needed, Decision 0168, item 2). *Search* is the provider's own (`manifest.search: provider`) where the loop can use it: the model's LiteLLM provider is in `runner_tools.NATIVE_SEARCH_PROVIDERS` and LiteLLM's shipped model map shows `supports_web_search`. Each call then carries `web_search_options: {search_context_size: low}` (at most one search per call, so the step's limit bounds them) and defines no `search` function. LiteLLM returns the provider's searches as calls named `web_search` that were already run: the loop records each (`{tool: search, by: provider, args, results}`) and counts it against the limit, never runs or answers it, keeps it out of the history it sends back, and sends the results (`[{title, url, …}]`, at most ten) as an outside-data message. Only `anthropic` is listed, checked in the litellm 1.108.3 source on 2026-11-18 (its hosted `web_search` tool sits beside the function tools; results in `provider_specific_fields.web_search_results`); LiteLLM drops Gemini's and Vertex AI's search tools when function declarations are present, drops `web_search_options` for xAI on chat completions, and does not take it for OpenAI's GPT-5 family, so those are not listed; adding a provider needs the same check. *Search through a declared service* (`manifest.search: <provider>`, §6.4): a `search(query)` function returning at most ten `{title, url, snippet}`; a failed search is refused back to the model naming only the error's type, so no key or address reaches the record; each is a row `{tool: search, by: <provider>}`. *`fetch(url)`* makes an HTTP(S) GET: the host is resolved once and every address must be public (`ipaddress.is_global`, not multicast), the connection goes to that checked address with the host's TLS name, redirects (at most five) are checked the same way, a URL with a user name is refused, at most 2 MiB is read with a 20 s timeout, HTML becomes readable text (scripts and styles dropped), plain text and JSON are returned as they are, PDF and other types are refused, and at most 50,000 characters come back as `{url, content_type, title?, text, truncated?}`. **A step that reads the project and the web at once** (both `read_file` and `fetch` offered; Decision 0168, item 6): `fetch` opens only a URL, compared without its fragment, that appeared in this attempt's search results (for provider search, its results and citations) or in the packet's `INSTRUCTIONS.md` and inputs; a URL named only by a fetched page is refused, and the system message says so. Search engine result pages are never scraped. Each call is a row of `tool_calls.jsonl` in the attempt folder (`{n, tool, args, bytes, sha256, ms, refused?}`; `finish` is the last row, with its arguments' size and hash), and the messages go to `~/.baton/logs/<run>/<step_path>/attempt-<n>.transcript.json`, machine-local because they hold whole files. A step needing no tooling the runner provides gets no `tools` key and makes one call, byte for byte as before. **Usage** (Decision: [0177](../decisions/0177-capability-check-details.md), item 2). The runner counts every model call of an attempt and writes `usage.json` beside the packet: `{calls, input_tokens, output_tokens, cost_usd, seconds}`, the cost being LiteLLM's figure for each response (`_hidden_params.response_cost`, else `litellm.completion_cost`) or `null` when it has none. It is a record, never a protocol: intake does not read it. Capability checks report it (§6.4); later slices of `2026-11-model-assessment` add it to the track record of shadow attempts, trials and steps.
- **`subprocess_harness`** with presets **`claude_code`** (`claude -p <prompt> <args>`) and **`codex`** (`codex exec <args> --skip-git-repo-check --color never <prompt>`); flags checked against `claude` 2.1.319 and `codex-cli` 0.166.0. Prompt: "Read <packet>/INSTRUCTIONS.md and follow it exactly; write outputs to <result>/ …". `cwd` is the attempt directory for `workspace: none`, the project root for `read` and `write`. `executable` defaults to `claude` / `codex`; `model` is passed as `--model`. The CLI uses its stored login (`auth.mode: cli_login`, env `allowlist`) or an injected key (`api_key`); `auth.mode: none` is a configuration error.
  - **Built-in args per mode** (a profile's `args.<mode>` replaces one mode's default): `claude_code` write `--permission-mode bypassPermissions`, read and none `--permission-mode acceptEdits`; `codex` `--sandbox workspace-write` for every mode.
  - **Tool args** (Decision: [0085](../decisions/0085-harness-tool-maps.md)). The args that turn a tooling capability on are researched data: the harness provider's `tools` map in the known-workers data (§6.4), read by the adapter for the profile's `provider` (else its adapter name). The adapter only places them. A dispatch gets the `args` for each mapped capability the step requires (`requires` plus its workspace mode's) and the profile claims, and the `off_args` for every other mapped one, so a step that does not need the web does not get it (least privilege). An arg goes among the mode args, or with `position: before_subcommand` right after the executable (`codex --search exec …`). The seed maps, entered by hand from `--help` until research replaces them: `claude_code` `web_access` on `--allowedTools WebSearch,WebFetch`, off `--disallowedTools WebSearch,WebFetch`; `codex` `web_access` on `--search` before `exec` **[VERIFY that exec honours it]**. The other tooling capabilities come from the mode args. `dispatched` records `tools {on, off, args}` and the CLI's `harness_version` (`--version`, cached per executable file).
  - **Event stream and evidence.** A dispatch's output is the CLI's machine-readable stream (`claude … --output-format stream-json --verbose`; `codex exec … --json`), saved as the attempt's log; intake still reads only `result.json`. When the attempt ends, the runtime scans the log for each capability turned on (`tool_evidence.py`, the tool map's `evidence` names: Claude Code `tool_use`/`tool_result` blocks and the result's `permission_denials`; Codex `web_search` items). A successful call records the capability `verified`; a denial records it `absent` and the attempt is classified `platform` / `capability_absent` (§8.8); a step that did not use the tool records nothing. No extra model call is made to verify. A dispatch with tools turned on to an SME records them too (`sme_requested.tools`).
  - **Read and none steps are enforced by the runtime, not by flags.** The attempt's `result/` lies inside the project, so every mode must allow some writes and no CLI flag confines them to `result/`. For workers that can touch files (harness and `command` adapters), the runtime snapshots the working tree (HEAD, plus every changed or untracked path with its content hash, excluding the attempt directory; ignored files are not seen) before and after the worker runs. Any difference fails the implicit `workspace` gate and **escalates** the step (`workspace_modified`, listing the paths). HEAD moving only through Baton's own checkpoint commits (`baton(…): …` subjects, descending from the earlier HEAD; this run's or another's) is not a difference (found in Phase 14: consulting an expert about a just-completed run releases its lease again, and that checkpoint was blamed on the expert). The runtime never reverts the change; the owner inspects it. Write steps are not checked here (protected paths, §9.4, are). The snapshot's `git status` uses the repository's own line-ending settings, not `core.autocrlf=false` (found on Windows CI in Phase 16: files the owner's git committed with `autocrlf=true` are CRLF in the tree and LF in the index, and a forced override reported them modified only when git happened to re-hash them, so two snapshots of an untouched tree could differ); the hashes are of the raw bytes either way.
  - **Failure signals**: lines such as "Not logged in" or "Invalid API key" classify an exit without a result as `platform` / `auth_failed`; an unknown-option error (`error: unknown option '--…'`, `error: unexpected argument '--…'`) as `platform` / `harness_flag_rejected`. A rejected flag opens a platform incident like any platform failure (§12.3), so the platform SME is consulted and proposes the data fix, and the capabilities turned on for that attempt become `absent` on the profile until the data is fixed (the owner resets them, §6.1) or the CLI's version changes.
- **`command`**: a configured command line with placeholders (`{prompt_file}`, `{packet}`, `{result}`, `{workspace}`), for other tools or for relaying to another agent. It is split like a POSIX shell would split it (no shell runs it; on Windows a backslash is an ordinary character, so `C:\tools\x.exe` stays intact); placeholders are substituted per word with POSIX-form paths (`{workspace}` is empty for `none` steps); the first word is the executable, resolved per §6.2.
- **`manual`**: prints the packet path and waits for `submit`. Used for humans and physical-world work.
- **`program`**: runs a program a recipe ships (§5.9) for a program step, with no model (Decisions: [0154](../decisions/0154-tool-steps.md), [0156](../decisions/0156-tool-steps-details.md), [0158](../decisions/0158-tool-steps-no-python-download-scratch-cwd.md), [0159](../decisions/0159-tool-runs-env-inputs-build-outputs.md)). No profile on the machine uses it: the runtime makes one in memory for the step, `program:<id>` (creator `program`), with a `clean` environment holding only the secrets the program names in `reach.secrets` (each resolved as `secret:<NAME>` is, §6.1, so a missing one refuses the dispatch as `configuration`). A machine profile with `adapter: program` is never eligible. Before the attempt is recorded, the dispatch finds the program's environment, or builds it: `uv python find --no-python-downloads --system` for a Python that fits `runtime.version` (never downloaded), then `uv venv` and, when the lock lists anything, `uv pip install --require-hashes -r <lock>`, in `~/.baton/programs/<lock sha256>-py<major>.<minor>/` (§4.4), reused by every project and program with the same lock and Python; `env.json`, written last, marks it complete, and a file lock keeps two builds apart. A missing uv or Python, or a failed build, is a `platform` failure: nothing is dispatched, the step stays ready and an incident says why (§12.3). The child is `python -m baton.program_runner`, as `litellm_api` runs `worker_runner`. It writes the inputs file (one JSON object keyed by input name: a JSON input is its value, any other `{path, media_type}`, a `many` role a list in order), makes a fresh, empty scratch folder outside the repository (the working directory) and an empty output folder, and runs the entry command with `{input}`, `{output}`, `{program}` and `{workspace}` filled in and its first word found in the environment's `bin` folder only; no shell runs it, and no `BATON_*` variable reaches it. Exit 0 with a JSON object in `output.json` and nothing in the output folder but it and the declared artifacts (`<name>` or `<name>.<ext>`, one file each) is `completed`, the artifacts copied into `result/artifacts/`; anything else is `failed`, the notes giving the reason or the exit code and the last 20 lines of the program's error output, with the values of its secrets masked. The program runs in its own process group (POSIX) or job object (Windows), with its output written to files, not pipes; once it has exited, any process still in the group or job is ended and the result is `failed`, naming it: a program keeps no service running (Decision 0155, item 4; Decision: [0164](../decisions/0164-builder-engineered-tools-details.md), item 6). A process that deliberately leaves the group (`setsid`) is not found. A program cannot return `blocked` or questions. For a waiting step (§5.9) the runner is given `--wait`: `output.json` must also hold a boolean `met`; met, `met` is removed and the rest is the output; not met, the runner writes `not_met.json` in place of `result.json` and keeps nothing else; otherwise the result is `failed`. A later check (`baton waits check`, §8.7) runs the same command in the foreground with no supervisor, under the same constructed environment, into the attempt's `check/` folder, with the step's effort band as its limit and the same working-tree check; its output goes to `~/.baton/logs/<run_id>/<step_path>/attempt-<n>.check.log`, replaced by each check. A command not found in the environment writes no result: `baton-worker: failure=platform code=program_command_missing`. Read and none steps get the working-tree check below, as for any worker that can touch files.

Adapters never interpret results; intake does.

### 6.4 Worker setup

**The track record** (change `2026-11-model-assessment`; `assessment.py`). What real work showed about each model is kept machine-wide in `~/.baton/track-record.yaml` under `models:`, beside the last-check records under `profiles:` (below), which are unchanged. Evidence belongs to a route, keyed by `model_id`, adapter, provider, invocation identifier and endpoint (`base_url`), never by profile name alone, so reusing a name carries nothing across; a route with no `model_id` (an alias) records nothing and is never a candidate. Each route keeps the harness version and the model's rating (its tier): a new harness version starts the record afresh when it is next written, and a new rating makes the old standing void at once. Every attempt of a worker step that ends adds an outcome by the tier of the step (no tier: `basic`) with its kind (`trial`, `shadow`, `step`; a shadow's at `strong`, written once it and its primary have ended, §8.7), its capabilities and its measured cost: a pass at `step_passed`, a failure at a rejected result or failed blocking gate (a trial's at `trial_failed`); platform and configuration failures are not evidence. An outcome's id is its run, step path, attempt and kind, so intake seen twice records once. Totals by tier and kind, and the last 100 outcomes, are kept. **Standing** at a tier comes from the counted trial and shadow outcomes there (Decisions: [0176](../decisions/0176-model-assessment-details.md), item 5; [0182](../decisions/0182-assessment-grading-put-back-budget.md), items 2 and 3): `put_back` with 2 failures in the last 5; otherwise `proven` after 5 passes with none of the last 5 failed; otherwise `candidate`. The thresholds are machine settings (`proven_after`, `put_back_after`, `window`). Proven ends trials at that tier and changes no eligibility; put back treats the model as below that tier (§8.4). The owner promotes or puts back by hand (`baton workers standing <profile> --tier <t> --promote|--put-back|--clear`, or **Promote** on the setup page); evidence after a promotion can put the model back again. A change of standing is recorded in the run (`model_standing_changed`) and returned as a notice the Director passes on (§13.3); `workers status` and the page list put-back models. Decision: [0179](../decisions/0179-trial-and-shadow-routing-details.md), item 5.

Writing profiles by hand needs knowledge that is not the owner's: model strings, capabilities, which adapter reaches which model. Three parts keep that work out of the owner's way, each with its own job (Decision: [0074](../decisions/0074-worker-research-and-resources-separate.md)): maintainers research models into shared data; the worker resource manager turns that data, plus what this machine has and what the owner declares, into profiles; `init` and `doctor` only confirm the machine is ready.

**Known-workers data** (`defaults/known-workers.yaml`, `baton-known-workers/1`; Decision: [0080](../decisions/0080-known-workers-format.md)) ships with the runtime, read-only, beside the adapters (`known_workers.py` validates it):

| Section | Holds |
|---|---|
| `machine_dependent` | Capabilities never listed in this data, because they depend on the machine (`loopback_network`): a profile gets one only from the owner's declaration or a probe (Decision: [0082](../decisions/0082-machine-dependent-capabilities.md)) |
| `models` | Keyed by `model_id` (§6.1): `creator`, intrinsic `capabilities` with a `capability_basis` for each (Decision: [0088](../decisions/0088-capability-basis.md)), `tier`, `context_tokens`, `category` (`llm`, `vision`, `transcription`…), `sources` (`url`, `retrieved`), `researched`, `retired` |
| `providers` | How access is obtained: `kind` `direct_api` \| `intermediary` \| `harness` \| `local` \| `openai_compatible`, with sources. A harness has `creators` (whose models it can run, Decision: [0089](../decisions/0089-harness-coverage-check.md)) and a `tools` map: for each tooling capability, `args`, `position`, `off_args`, the `help` args and `flag` that setup checks, the `evidence` names its event stream shows, `versions` and `sources` (§6.3; Decision: [0085](../decisions/0085-harness-tool-maps.md)) |
| `routes` | One way to run a model: `model_id` (or, for a mutable alias, `alias: true` and a `creator`), `provider`, `adapter`, `invocation` (the profile's `model`; empty only for a harness's default model, and a harness pinned to a model is a route like any other: `model_id` plus the invocation it passes as `--model`), `supported`, the capabilities the route adds (a harness's tools, with their `capability_basis`), `tier`/`context_tokens` for an alias route, `sources`, and `verified` (`date`, `tool`, `version`) only for an actual live check |

A **capability basis** says why a capability is claimed, never that it was proved: `documented` (a source), `catalog` (the LiteLLM model-map field that shows it: `supports_response_schema` → `structured_output`, `supports_function_calling` → `tool_use`, `supports_vision` → `vision`) or `judgment` (a one-line reason: the creator class's normal capabilities). Every claim ships as `likely` and is checked by use (§6.1); a capability with no basis is omitted. The field is optional in the format (so it stays `baton-known-workers/1`) and required of research proposals. Research claims and live checks are separate fields, so an unverified finding is never shown as tested. Research may cover models no adapter can run yet: such a route is `supported: false` and never becomes a profile. Validation checks the schema, the capability and tier vocabulary, that a supported route names an existing adapter, that every route's model and provider exist, that a `model_id` starts with its creator, that machine-dependent capabilities are absent, provenance on every model, and duplicate routes. Vendors and models here are profile data, like the adapters; recipes stay model-neutral and their lint is unchanged (§5.3).

**Research** (Decision: [0083](../decisions/0083-researcher-dispatches-through-a-profile.md)) is for maintainers, from a source checkout only: `baton-worker-research --profile <name>` (its own package in `tools/worker-research/`, installed with `uv tool install --editable tools/worker-research`; it updates the checkout it was installed from unless `--repo` names another) runs the one-step `worker-research` recipe in a scratch project, dispatched to a profile on the maintainer's machine (`web_access`, `file_write`, `structured_output`, `technical_reasoning`). The worker covers the landscape systematically (frontier and alternative creators, open-weight models, intermediaries, distribution hubs and local runtimes, every category that can do a bounded job on its own) and returns the proposed file plus a report of its inclusion criteria, coverage and coverage gaps. Its packet also carries (Decision: [0091](../decisions/0091-researcher-inputs-and-model-listing.md)) the harness providers' current tool maps, the vocabulary's tooling capabilities, the maintainer's starting documentation URLs for each harness (`tools/worker-research/harness-docs.yaml`), the installed LiteLLM's model-map entries for every API route in the data (the report records the LiteLLM version), and a validator command (`baton-worker-research --check <file>`) the worker may run on its own proposal. It proposes, for each harness provider, its `creators`, one pinned route per current model the CLI documents (plus the default alias), the tool map and the flag for machine-readable events (Decision: [0090](../decisions/0090-harness-flags-are-researched-data.md)); every capability it claims carries a basis (0088). The report lists, per harness, the models routed, those not routed with the reason, the tools proposed and any flag that widens permissions. A harness's `creators` name whose models it can run, so a harness other than Claude Code and Codex needs data, not code; dispatching to one still needs an adapter preset, and until then its routes are `supported: false`. The script validates the proposal and refuses one that touches `verified`, or that claims a capability with no basis; a valid one replaces `defaults/known-workers.yaml` for review with `git diff`, and the report goes to `tools/worker-research/reports/<date>.md`. Baton's wheel ships `defaults/` and nothing from `tools/` (a test builds both wheels).

**The worker resource manager** (`resources.py`; `baton workers status | setup | declare`, §13.1; Decisions: [0077](../decisions/0077-workers-command.md), [0078](../decisions/0078-machine-resources-file.md), [0079](../decisions/0079-generated-profiles-directory.md), [0081](../decisions/0081-live-verification-on-request.md)) combines three inputs:

1. The known-workers data, read-only.
2. **Discovery**: for each harness provider with a supported route, is its CLI found (the minimal PATH, then `nvm` and `~/.local/bin`, §6.2), and does it report a login (the adapter's auth status; no model call)? Not installed, or not logged in, is reported in plain words with what to do. Discovery also reads the CLI's version and checks each tool-map flag against its `--help`: a harness profile gets a tool-map capability only when the flag is shown, and setup reports the ones not offered on this machine (0085).
3. **Declarations** in `~/.baton/resources.yaml` (`baton-resources/1`), for what discovery cannot find:

```yaml
format: baton-resources/1
resources:
  openrouter-main:
    kind: worker                     # required; the only kind so far
    provider: openrouter
    credential: secret:openrouter_main   # only ever a reference (§6.1)
    models: []                       # optional allowlist of model_ids
  claude-here:
    kind: worker
    provider: claude_code            # facts about a discovered harness
    capabilities: [loopback_network] # machine-dependent only, declared by the owner (0082)
setup:
  worker: { completed: 2026-11-06, runtime: 0.1.0, nothing_more: true }
```

Every resource names its `kind`, and setup state is kept per kind, so later kinds of resource share the file; an unknown kind, a missing kind, a literal credential or a capability that is not machine-dependent is refused.

**The declared search service** (Decision: [0168](../decisions/0168-step-tool-harness-details.md), item 3). One per machine, under its own top-level key, since it is not a worker account: `search: {provider, credential?, base_url?, note?}`, written by `baton workers declare --search <provider> [--credential secret:<NAME>] [--base-url <url>] [--note …] [--remove]` (CLI and MCP). The provider is any of LiteLLM's search providers (`litellm.types.utils.SearchProviders`; checked when declaring, since reading it loads LiteLLM); a `searxng` service needs `base_url` and no key; a credential is only a `secret:` reference; declaring another provider replaces the service and its fields. Baton has no code per provider: the runner calls `litellm.search(query, search_provider, max_results=10, api_key, api_base, timeout)` (§6.3). With one declared, every `litellm_api` profile whose model calls tools has `web_access` (§6.1), its provider's own search still first where the loop can use it. At dispatch the key is resolved into the child's environment as `BATON_SEARCH_API_KEY` (listed in `dispatched.env.secret_names`, redacted like any secret), and the provider and address go on the child's command line (`--search-provider`, `--search-base-url`), not into the packet: they are the machine's, not the run's. `workers status` shows the service (`search`).

Capabilities from the data, from a tool map or from a declaration are claims: each starts `likely` and the work itself makes it `verified` or `absent` (§6.1; Decision: [0084](../decisions/0084-capability-states.md)). No extra model call verifies one unasked: real dispatches are the checks, `--verify` stays the only live check of a route (0081, amended), and capability checks run only when the owner asks (below; Decision [0175](../decisions/0175-model-assessment.md)).

`baton workers setup` turns each supported route into a profile when its provider is reachable: a harness that discovery found logged in (availability `detected`), or a declared resource for that provider, within its `models` (`declared`). The profile takes the model's capabilities, tier and context size plus the route's, the owner's declared machine-dependent capabilities, the provider's `env_deny`, and for an API route `auth: {mode: api_key, env: {<provider's api_key_env>: <credential>}}` and the resource's `base_url`. Names are `<provider>` for a harness default, else `<resource or provider>-<model name>`. A name an owner profile already has is skipped and reported. New files are written atomically to `~/.baton/workers/<name>.yaml` with `generated: {by, known_workers_sha256, availability, verified?, content_sha256}`; an existing generated file follows the refresh rules below. The run records `setup.worker.completed`.

**Listings** (Decisions: [0109](../decisions/0109-listing-sources.md), [0110](../decisions/0110-unjudged-model-default-tier.md), [0112](../decisions/0112-listing-model-identity.md), [0113](../decisions/0113-listing-filter-and-exclude.md); `listings.py`). A listing is the list of models a provider says it offers, fetched deterministically (no agent) by `baton workers refresh` and cached in `~/.baton/listings/<provider>.json` (`baton-listing/1`: provider, source, fetch date, models). OpenRouter's public `GET /api/v1/models` is the first source. A failed fetch (network, malformed response) is reported in plain words and recorded as a diagnostic (`listings.fetch_failed`); the last good cache stays. `workers setup` also plans a profile for each listed text model whose listing shows `response_format` or `structured_outputs` (the `litellm_api` reply contract, §6.3), for each declared resource of that provider, unless a researched route already has that invocation. Such a profile takes `context_tokens`, `price` and catalog-basis capabilities (`structured_output`, `tool_use`, `vision`) from listing fields, tier `basic`, and a `model_id` that is the researched route's when the invocation matches, else the lower-cased `canonical_slug` (unknown for an alias or router). A listing never adds a judgment capability and never marks anything `verified`. **Assessed models** (Decision: [0111](../decisions/0111-owner-run-assessment.md)). `~/.baton/known-workers.local.yaml` (`baton-known-workers/1`) is the owner's overlay: the result of an assessment of chosen models. It holds `models` and `routes` only, adds models and never edits or replaces a shipped one, never carries `verified`, and each model it adds needs a basis for every capability it claims, as a research proposal does; the merged data passes the validator above, and a problem refuses the run in plain words. A listing profile whose `model_id` is in the merged data (researched or assessed) takes that model's `creator`, `tier` and capabilities in place of the `basic` default (Decision [0110](../decisions/0110-unjudged-model-default-tier.md)), with the listing's own context and price. The overlay can be offered upstream as a candidate change to the shipped data. `baton workers assess <model_id>… --profile <name>` produces an overlay entry (Decision: [0120](../decisions/0120-assessment-recipe-fetched-pinned.md); `assess.py`). It accepts only models some listing of the owner's offers under that identity and that have no judgment yet. It runs the one-step `model-assessment` recipe through the named profile (it needs `web_access`, `file_write`, `structured_output`, `technical_reasoning` and tier `strong`, like research) in a scratch project. The packet carries the listing facts for each model, the vocabulary, the installed LiteLLM's entries and a validator command, `baton workers check-overlay <file>`, which the worker may run on its draft. The recipe is not in the wheel (0083 stands): it is fetched from the repository named by `launcher.yaml`'s `source`, at the tag `v<version>` of the running runtime (never latest), and cached in `~/.baton/assessment/<version>/`; with no network and no cache `assess` refuses and says an overlay can be written by hand. The runtime's own validator (`known_workers.merge_overlay`, the same code that loads the overlay) checks the worker's draft merged into the owner's existing overlay, and nothing is written if it refuses. Models the worker returns beyond those asked for are dropped. A report goes to `~/.baton/assessments/<date>.json`; `workers setup` then applies the new tier and capabilities to the model's listing profiles.

**Tiers from published evaluations** (change `2026-11-model-assessment`, slice 2; Decisions: [0175](../decisions/0175-model-assessment.md), [0176](../decisions/0176-model-assessment-details.md), item 1, [0178](../decisions/0178-evaluation-tiers.md)). A model (or an alias route) may carry `tier_basis`: `{kind: evaluation, evaluations: [<result>], supporting?: [<result>], reason?}` or `{kind: judgment, reason}`, a result being `{name, version, score, configuration?, source: {url, retrieved}}`. A capability basis may be `{kind: evaluation, evaluation: <result>}`. `defaults/evaluation-tiers.yaml` (`baton-evaluation-tiers/1`) is the shipped mapping: per evaluation its `title`, the `url` of its method, whether it is `independent` (the publisher tests the models itself) and `decides_tier`, thresholds per `version` (the lowest score for `strong` and `standard`; scores of different versions never compare, so a new version needs its own entry) and `grants` (capability → the lowest tier at which a result grants it). It ships the Artificial Analysis Intelligence Index, which decides (v5.0.1: `strong` 50, `standard` 25; grants `technical_reasoning` at `standard`), and the LMArena text leaderboard, supporting only. The validator (`known_workers.validate`, used for the shipped data, the overlay, `workers check-overlay` and assessments) refuses an unknown evaluation or version, a supporting-only result cited as deciding, an evaluation basis with no deciding result, deciding results that are all vendor-reported without a `reason`, a capability the result's evaluation does not grant or at a score below its level, and a tier other than the one the deciding results give: each result's tier by the thresholds, and with several, the lower median. A tier basis is optional in the format (`baton-known-workers/1` stands); a tier without one is research's judgment, as before. **The 2026-11-19 refresh** gave an evaluation basis to the shipped models Artificial Analysis scores (among them Opus 5.5 59, Sonnet 5.5 55 and GPT-6.1 Terra 51, `strong`; Haiku 5.5 36 and GPT-6 Luna 28, `standard`, now with `technical_reasoning`; gpt-oss-120b 4 and DeepSeek V4 Pro 23, `basic`) and added the models most used through OpenRouter that it scores, with Fable 5.2 (65) and the current Gemini 4 and GPT-6.2 models, each keyed by its OpenRouter canonical slug so the account's listed workers take the tier and keep their listing's price. Fable 5.1, which it does not score, keeps a judgment basis with LMArena as support. The maintainer's research recipe and the owner's assessment (`baton workers assess`, and **Rate … from published evaluations** on the setup page, §13.9) receive the mapping as the input `evaluations` and are told to tier from it; both recipes are at version 2, and the assessment recipe takes the input as optional so an earlier runtime's fetch still works.

**The provider directory** (Decision: [0117](../decisions/0117-provider-directory.md)) is the `providers` section with optional directory fields: `display_name`, `base_url` (an `openai_compatible` provider's endpoint; a resource's own `base_url` overrides it; the validator refuses it on any other kind) and `signup_url` (where the owner gets a key). A directory provider needs no researched model: its models come from its listing. A resource for one needs only a credential (none for a local runtime). Entries so far, each endpoint and key page fetched 2026-11-10: Together AI, Fireworks AI, Cerebras, DeepInfra, Chutes and Requesty, and the local runtimes Ollama, LM Studio and vLLM at their documented default ports. Which of them offer a free or cheap tier is not claimed; a maintainer research run adds that and further providers, as it does models.

**Account list, quota figures, summary and switch** (Decisions: [0109](../decisions/0109-listing-sources.md), [0113](../decisions/0113-listing-filter-and-exclude.md), [0114](../decisions/0114-quota-exhausted-reroutes.md)). With a credential declared, `workers refresh` reads OpenRouter's per-account list (`GET /api/v1/models/user`, only what the account's provider preferences, privacy settings and guardrails allow) in place of the public one, and falls back to the public list, saying so, when that read fails. It also reads the key endpoint (`GET /api/v1/key`: credit and `free_model_daily_requests`) into `~/.baton/listings/<provider>.quota.json`, dated; a failed read keeps the last figures. `workers status` and `doctor` show those cached figures with their date and read no network; `doctor` warns when the free requests are used up. `workers status` summarises listing profiles by resource (count, free count, cheapest per tier, listing date, quota) instead of listing them; a profile marks itself a listing profile in its `generated` marker (`listing: true`). A resource has `enabled` (default true): `baton workers disable <name>` sets it false and routing leaves that account's workers out (`its provider account is switched off`), `enable` restores them, and nothing is deleted. Not built: subscription-CLI quota signals (the owner deferred them, 2026-11-10).

**The `openai_compatible` kind** (Decision: [0118](../decisions/0118-openai-compatible-kind.md)). Any endpoint that speaks the OpenAI API is a provider: the resource names the provider `openai_compatible`, a `base_url` (required; `declare` refuses without) and a `credential` (omitted for a local runtime). `workers refresh` reads `<base_url>/models` (with the key as a bearer token when there is one) into a listing cached per resource. Its profiles dispatch through LiteLLM's `openai/<id>` route with that `base_url` (a keyless one has `auth: none` and a placeholder `api_key`). The listing gives ids only: price and context stay unknown, identity is unknown (`model_id` absent, never independent, 0076), the creator is the id's prefix when it has one and `unknown` otherwise, and `structured_output` is claimed from the adapter's prompt-schema fallback (§6.3), `likely` and checked by use (0087). Checked on Linux: the API adapter's child reaches `127.0.0.1` (the clean environment removes only variables); a platform whose sandbox blocks loopback is the machine-dependent `loopback_network` question (0082), not tested here.

Fetching changes no profile: only `workers setup` writes or refreshes them, under the rules below.

**Capability checks** (change `2026-11-model-assessment`; Decisions: [0175](../decisions/0175-model-assessment.md), [0176](../decisions/0176-model-assessment-details.md), [0177](../decisions/0177-capability-check-details.md); `capability_check.py`). Baton ships short tasks per capability, graded by code only, in `defaults/capability-checks.yaml` (`baton-capability-checks/1`): three to five each for `structured_output`, `tool_use`, `workspace_read`, `long_form_writing` (length, structure and stated constraints only, never quality) and `technical_reasoning` (small problems with one right answer); `vision` has none until the runner can send images (0177). The set has one `version`, raised whenever a task changes. Each task is a prompt, an `output_schema`, optional `workspace` files and runner `tools`, an `expect_tokens` for the estimate and graders (`schema`, `equals`, `contains_all`, `excludes`, `words`, `headings`, `numbered`, `tool_called`); the loader refuses an unknown capability, grader or tool, a duplicate id and a path that leaves the working tree. They run only when the owner asks: `baton workers check [<profile>…] [--free] [--provider <name>] [--all] [--again] [--yes]` (CLI) or the setup page's **Check abilities** (§13.9), on generated profiles. First comes an estimate (`estimate {profiles [{tasks, capabilities, adding, input_tokens, output_tokens, cost_usd | cost}], tasks, cost_usd, unknown_price}`) from list prices; a subscription route says `included in the subscription` and an unpriced one says so, never guessed. The command runs on confirmation or `--yes`; without either, and in `--json`, it returns the estimate only. Each task is a tiny packet (`manifest.json`, `INSTRUCTIONS.md`, `output_schema.json`, with the files as a read-only working tree) run through the profile's own adapter in a scratch directory, as a step's packet is (API routes through the runner and its tool loop, harness routes in read mode), six models at a time but one model's tasks one after another (free routes allow few requests at once), each within 180 s; a rate-limited task waits 20 s, then 40 s, and is tried again, and a route still limited after that leaves its remaining tasks unrun for this check, its log in `~/.baton/logs/workers/<profile>-check-<task>.log`. A route checks the capabilities it claims, less any the owner declared `absent`; an unjudged listing profile (§6.4 listings: tier `basic`, its `model_id` in neither the data nor the overlay) on an API route is also checked for `structured_output` and `tool_use`, and an API route with `tool_use` for `workspace_read`, which its runner provides (§6.1). A capability whose tasks all pass is recorded `verified`, `by: check`, with `set_version`; a task that fails its graders is run once more, and a task that fails again records it `absent` with the failed tasks and their first reasons (Decision [0178](../decisions/0178-evaluation-tiers.md), item 4: one bad answer is not decisive; the retry's result carries `first_try`); a task that could not run (no answer in time, an auth, quota or provider failure) records nothing for its capability, and the check is incomplete. `tool_called` is graded from the runner's `tool_calls.jsonl` and is not applicable on a harness route. A passed `structured_output` or `tool_use` on an unjudged profile is kept as `adds` and `workers setup` adds it to that profile's capabilities (Decision 0176, item 3), which the check runs at once; `technical_reasoning`, `long_form_writing` and the tier never come from a check. **The track record** is `~/.baton/track-record.yaml` (`baton-track-record/1`); its last-check records are under `profiles:`, keyed by profile (one model on one route; the evidence from real work is under `models:`, above), written under a lock: each profile's `model_id` and its last check `{set_version, date, complete, capabilities {<cap>: {result, passed, failed?, error?, cost_usd?, seconds}}, adds?, cost_usd?, cost?, seconds}`, the cost being the sum of the runner's `usage.json` figures and the seconds measured around each task. A profile already checked, completely, under the current set version is skipped, unless the owner asks `--again` or its route is an alias (no `model_id`: the model behind it may have changed). `workers status` shows each checked profile's last check (`capability_check {set_version, date, complete, results, cost_usd | cost, seconds, adds?}`), and the setup page its date and cost.

**Live checks** run only for `--verify <profile>` / `--verify-all`: one no-op round trip through the adapter, as `doctor`'s (§13.4). A pass records `verified {date, adapter, runtime}`; a new profile that fails is not written, and an existing one keeps its file, with the failure reported. Unverified profiles are eligible for dispatch, and `workers status` lists them as unverified.

**Refresh and repeat runs** (Decision: [0079](../decisions/0079-generated-profiles-directory.md)). Only `baton workers setup` changes generated profiles; installing or upgrading the runtime changes none and adds none, so newer known-workers data shows up as `available_not_generated` in `workers status` until the owner runs setup. On a run:

- A file whose `content_sha256` no longer matches its content is the owner's (`edited`), and so is a file without the marker: never changed, refreshed or removed.
- An untouched file may have only `capabilities`, `tier` and `context_tokens` refreshed. If its binding would change (`adapter`, `creator`, `model_id`, `provider`, `model`, `resource`, `auth`, `options`), it is left as it is and the run says why; a new binding is a new profile.
- A profile the inputs no longer offer is kept and flagged in `workers status`, never removed. The flag gives one specific reason, the first that applies: its model is retired; its harness is not usable here (not installed or not logged in); its resource is gone, no longer lists the model or has no credential; no route in the catalog in use produces it; or its route is skipped for another reason (the `plan_profiles` reason). When the profile's `known_workers_sha256` differs from the catalog in use, the route-gone flag says it was generated from a different catalog (both short shas), since a different Baton runtime sharing `~/.baton/workers/` is the usual cause. `workers status` names the known-workers file it read and its short sha256 (`--json`: `catalog`), and each flagged `generated.<name>` carries `flag_code` (`retired`, `harness_unusable`, `resource_gone`, `route_gone`, `skipped`) and `catalog_mismatch`. `workers setup`'s `kept` lines use the same reasons.
- Each profile is handled on its own: one failing (a write error, a failed check) is reported and the others go ahead. A repeat run with unchanged inputs writes nothing.
